# 四小时探索迁移任务

## 实验目标

使用本目录的 HarmonyOS 源工程，将核心交互和资料功能迁移到课程 OpenHarmony 开发板，再按设备条件接入任务执行。基础知识已在前课讲授，4 小时用于实际改写、运行和核对。

教师应先完成 Pura 80 源版真机验收，准备 OH SDK、签名、图库与文件管理服务、中文输入法、模型服务和设备控制环境。不能把“源码编译过”当作“源版已经能跑全部任务”。

## 时间安排

| 时间 | 小目标 | 证据 |
| --- | --- | --- |
| 0–15 分钟 | 跑源 App、读两条调用链、列差异假设 | 基线记录和平台依赖表 |
| 15–50 分钟 | 改构建、签名、安装、冷启动 | 编译与安装结果、目标页面 |
| 50–90 分钟 | 真实选图、确认导入、取消、预览 | Picker 与实际图片 |
| 90–130 分钟 | 中文文件、空文件、超限、错误格式 | 内容核对与异常恢复 |
| 130–160 分钟 | 文本/图片请求、笔记、重启恢复 | 请求检查结果与恢复结果 |
| 160–205 分钟 | 检查 DeviceExecutor，接入目标执行方式 | 一次真实任务和一次取消 |
| 205–220 分钟 | 必做修复或一个小扩展 | 复测或扩展演示 |
| 220–240 分钟 | 完整验收与提交 | HAP、源码、报告、演示 |

如果 OH self-HDC 协议实现已由教师提供，学生工作聚焦接口接入、能力判断和行为回归；不要求在四小时内从零写调试协议。若执行能力准备不足，标注该阶段未通过并继续其他独立功能，不用回放冒充实际操作。

## 第一步 先提出迁移假设

不要立即全局替换。检查构建产品、deviceTypes、权限、SDK 起始版本、系统应用依赖、网络地址和执行器。每项标记“能共用 / 需要修改 / 待实测”，给出文件位置。

AI 提示词：

```text
请阅读这个 HarmonyOS ClawMate 工程，目标是课程的 OpenHarmony API 18 开发板。
先画出资料问答与 GUI 任务的调用链，列出平台依赖，不修改代码。
区分编译 SDK、目标版本与最低兼容版本。
不要把所有 @kit 或 ohos 名称当作不兼容，也不要假定系统服务一定存在。
```

## 第二步 每次只验证一个链路

建议逐步通过：启动 → 文本请求 → 文件导入 → 选图 → 附件请求 → 笔记恢复 → 设备执行。遇到错误记录首个有效报错和触发步骤，再让 AI 给最小修改。

```text
以下是目标设备信息、首个报错和相关代码。
请判断是工程配置、API 版本、权限、缺少系统服务还是业务逻辑问题。
只修改解决该问题所需的部分，解释原因，给出实机验证步骤。
不要删除必做功能、返回固定成功或任意移除系统能力声明来掩盖故障。
```

## 第三步 替换设备执行器

阅读 `platform/DeviceExecutor.ets`，定义目标实现。至少处理：初始化、目录与能力、启动、截图、动作、取消、返回、关闭。

OH 有 self-HDC 的环境时，连接本机调试服务并构造动作；没有该环境时，先由教师明确可用通道。保留 AgentRunner 的取消、终态和每步截图确认规则。

```text
请根据 DeviceExecutor 接口设计 OH 适配方案，先列出实现与验证步骤。
业务循环不直接依赖 HDC。截图尺寸、0–1000 坐标、中文输入、取消和清理必须一致。
能力缺失时明确失败或暂停，不返回假的 success。
```

## 探索题

- 给笔记增加关键字搜索或标签，并在重启后恢复。
- 清理未引用资料副本，证明不会误删仍被其他笔记引用的文件。
- 导出一条笔记为 UTF-8 Markdown，处理用户取消和保存失败。
- 在只改执行器的条件下，支持两个平台运行，并解释实际共用的代码。
- 设计一项任务完成的确定性检查，比较它与模型说“done”的差别。

## 提交要求

提交独立源码、签名 HAP、[迁移报告](05-report-template.md)和约两分钟录像。录像覆盖真实选图、中文资料、笔记恢复、一个真实设备任务与取消；较长流程可提交连续录像并在报告中标时间点。

使用测试服务、测试替身或教师救援代码的地方如实注明；不以代码行数多少评分。能用实际证据说明某一共同 API 无需修改，同样属于迁移成果。
